## 01 · 核心判断：VLN 是闭环决策，不是给导航加一句话 {#overview}

视觉语言导航（Vision-and-Language Navigation，VLN）要求机器人将自然语言、当前视觉观测和历史信息联系起来，持续决定向哪里移动、何时回看、何时停止。语言可能规定沿途顺序，而不只是终点：走到同一个地方，未必完成了同一条指令。[1][2][3]

**本文判断：对于已有定位、建图和导航基础的工程团队，优先建立“语言与空间状态 → 子目标 → 可执行导航 → 结果验证”的分层闭环，再研究学习策略能替换其中哪一层。** 这是一条便于定位问题的工程路线，不是声称端到端方法没有价值。

截至 2026-11-11 核查的资料，领域已有从拓扑图模型、显式语义地图到视频 VLA 和异步双系统的多条路线。但论文中的高成功率、无地图输入或跨机器人演示，都不能单独证明机器人能够在陌生环境长期自主运行。本文不制作跨基准的成功率榜单，也未进行模型训练、真机复现或硬件性能测试。

| 阅读问题 | 本文结论 | 重点章节 |
| --- | --- | --- |
| VLN 和 ObjectNav 有何区别？ | 指令路径约束与类别目标搜索不同，不能混用任务指标 | 02、03 |
| 为什么有些高分方法很难接到机器人上？ | 候选点、定位、低层控制器、相机视角等假设可能不同 | 04、09 |
| 三维视觉有什么价值？ | 空间目标落地、可达区域、状态记忆、主动观测与失败归因 | 05、08、10 |
| 哪些代码适合先读？ | 经典图模型理解机制；InternNav 检查系统接口；StreamVLN 研究历史压缩 | 06、07、13 |
| 怎样证明进步？ | 同条件比较路径遵循、停止、时延、碰撞与人工干预 | 12、13 |

## 02 · 任务分类：目标、指令和机器人身体要同时定义 {#tasks}

经典 R2R 将人类路线描述与室内视觉环境关联；RxR 增加多语言及更细粒度时空对齐，不能简单理解成把英语指令翻译成其他语言。[1][2]

| 任务 | 目标输入示例 | 是否必须遵循指定路线 | 主要困难 |
| --- | --- | --- | --- |
| PointGoal | 去给定坐标 | 通常没有语言路径约束 | 定位、避障、到达 |
| ImageGoal | 去参考图片所在位置 | 通常不是逐句路线执行 | 外观匹配、跨视角重定位 |
| ObjectNav | 找到一张椅子 | 通常允许探索不同路线 | 类别搜索、探索、停止 |
| Instance / referring goal | 找靠窗的那把蓝色椅子 | 取决于任务定义 | 实例消歧、关系理解 |
| 路线指令 VLN | 穿过门，在第二个路口左转，停在沙发旁 | 是，顺序与地标可能都是要求 | 跨模态对齐、进度跟踪、回退 |
| 交互式导航 | 先询问“哪一个门”，再执行 | 含澄清或动态补充 | 对话状态、歧义管理、动作一致性 |

表中是任务辨析，不是统一基准定义。本文重点是具身路线指令导航，并将目标导航和移动操作作为接口问题讨论。NavFoM、Uni-NaVid 等统一多种导航任务，但共用模型不意味着这些任务可以共用一个没有条件说明的成功率。[10][15]

“去厨房”可以主要依赖房间检索；“穿过客厅，绕过桌子，从右边门进入厨房”还要求路径和次序一致。将整句指令只转成最终坐标，会丢失必须经过的中间条件。相反，遇到目标明确但路径已经被封堵的现实任务，还需要定义允许重规划的范围，而不是机械复述原路线。

## 03 · 从导航图到物理仿真：名字相似，问题并不相同 {#benchmarks}

R2R 在预设的离散视点图上选择下一步；VLN-CE 移除了只能沿导航图移动的限制，在连续环境里执行低层动作。**“连续环境”不意味着动作一定是连续速度：VLN-CE 典型设定仍可使用固定步长前进和固定角度转向。**[1][4]

| 平台或数据 | 适合研究 | 不能直接推出 |
| --- | --- | --- |
| R2R / Matterport3D 导航图 | 指令对齐、地标选择、全局图搜索 | 真实避障、足式稳定和连续控制性能 |
| R4R、RxR | 路径遵循、长指令、多语言与历史信息 | 动态家庭中的长期可靠性 |
| R2R-CE / RxR-CE | 连续环境决策、局部动作执行 | 电机延迟、轮地滑移和真实接触都已建模 |
| VLN-PE | 身体、控制、光照和观察空间对表现的影响 | 仿真通过即可替代实机验收 |
| NaVILA 的 VLN-CE-Isaac | 高层导航与足式低层控制的联动 | 不同身体和控制器分数可直接合并 |

R4R 强调路线遵循，RxR 的语言及对齐注释扩展了任务难度。[2][3] VLN-PE 的论文明确报告视觉与物理条件变化引起的性能下降，并覆盖轮式、四足与人形载体；这是评估部署差距的入口，不是保证迁移成功的工具。[16] NaVILA 则将高层 VLA 和低层运动技能拆开，展示物理仿真与真实机器人案例。[12]

阅读任何评测前先核对六项：传感器与视场、定位是否可用、地图是否预知、动作候选从何而来、底层控制器是什么、停止成功如何定义。尤其不能把使用真值导航信息的 ShortestPathFollower 与完全自感知局部控制当作同等条件。

## 04 · 技术路线一：记忆与拓扑图仍然有价值 {#graph}

将任务视作部分可观测决策：当前画面可能看不到目标，也不能证明经过了哪个相似门口。可以用历史状态近似保存任务进度与环境信息：

```text
h_t = Update(h_(t-1), observation_t, action_(t-1), instruction)
a_t = Policy(h_t, instruction, available_actions_t)
```

这是概念形式，不对应某个现成模型的训练代码。历史表示可以是循环状态、Transformer token、拓扑节点、语义地图或它们的组合。

DUET 的核心是全局图推理与局部跨模态理解的双尺度结合；ETPNav 把在线拓扑规划用于连续环境，通过局部可行候选逐步发展地图。[5][6] 借鉴点不是“图模型比大模型好”，而是把“下一处应该去哪里”与“当前能朝哪里行动”分开表达。

**工程边界：图中的边不能只代表视觉相似。** 它还需要可通行证据、方向、宽度及可能的失效状态。电梯、楼梯、关闭的门和不同楼层之间的关系，不应只根据嵌入距离直接连边。错误闭环或地点混淆会把后续推理带到一个错误但内部自洽的世界。

推荐保留访问历史、前沿候选、已失败边与当前子指令。对长程任务，比较“无历史／短窗口／显式拓扑／拓扑加状态失效”四组，比只增加上下文长度更容易解释收益。

## 05 · 技术路线二：显式三维语义地图与空间目标落地 {#maps}

VLMaps 将视觉语言特征融合到几何地图，并以语言检索空间目标；ConceptGraphs 以物体为节点，多视角关联形成三维对象和语义关系。[7][8] 前者有利于空间检索，后者便于表达对象关系；两者都不能直接替代保守的碰撞地图。

对于 RGB-D 观测，像素到地图坐标的概念关系是：

```text
p_camera = depth(u,v) · inverse(K) · [u, v, 1]^T
p_map = T_map_camera(timestamp) · p_camera
```

实际系统必须区分深度是沿光轴的深度还是距离，正确处理畸变、RGB/Depth 对齐、外参和时间戳。取检测框中心的单个深度值容易落到背景；更稳妥的候选方案是用分割区域的有效深度聚合，并对边缘、空洞和离群值降权。

**物体中心不是导航终点。** “走到柜子旁”应生成柜子前方的可达观察位姿，并检查机器人足迹、转向空间和视线；不能把二维投影点直接下发给控制器。关系词“左边”还要记录参照系：以机器人当前朝向、物体朝向还是房间布局为准。

本文建议用三层状态协作：几何层负责可通行和距离，语义层负责对象及关系，任务层负责需要满足的子条件。对象移动后，只更新对象坐标不够；旧位置的占据残留、关系边和任务假设也应失效。地图型系统的价值在于可查询、可回溯，但维护错误的地图有时比没有地图更危险。

## 06 · 技术路线三：视频 VLM / VLA 如何处理导航历史 {#video}

NaVid 用当前与历史 RGB 帧以及指令生成下一步动作；其模型对历史和当前画面采用不同的信息预算。[9] Uni-NaVid 将 VLN、目标导航、问答和跟随等任务纳入视频动作模型。[10] 这些工作说明视频语义可以直接参与决策，但“模型输入不使用地图或里程计”不等于机器人的全部执行链都不需要状态估计。

StreamVLN 以滑动窗口 KV cache 维护快速更新上下文，并用较慢更新的压缩记忆处理长视频。[11] 这里的“慢快”主要描述上下文管理，不应与下一节中独立的语义规划器和运动控制器混为一谈。官方仓库提供训练和评测入口，但具体部署仍需核查权重、场景数据和软件依赖。[23]

| 历史策略 | 好处 | 应单独验证的风险 |
| --- | --- | --- |
| 只看当前帧 | 开销低 | 相似场景、回访与指令进度丢失 |
| 固定最近窗口 | 状态新鲜、计算可控 | 长任务早期地标被遗忘 |
| 历史 token 压缩 | 降低长序列开销 | 小但关键的转向/门牌细节丢失 |
| 显式空间记忆 | 地点和任务状态可查 | 关联错误、旧状态过期 |
| 混合记忆 | 将短时视觉与长期状态互补 | 缓存、地图、实际位置不同步 |

**“记得更多”和“走得更可靠”不是同一目标。** 应记录记忆更新时机、丢弃策略、每步 token 数、缓存长度及失败原因；用重复走廊、折返、目标换位等场景测试，避免仅靠一段长视频论证长程能力。

## 07 · 技术路线四：慢规划、快执行与跨形态导航 {#dual-system}

NaVILA 的高层产生语言式导航命令，低层负责足式运动执行。[12] InternVLA-N1 / DualVLN 进一步使用像素目标及潜在计划连接高层 VLM 和局部轨迹策略；InternNav 将这些模型、仿真和评测接口放在同一工具箱中。[13][14]

截至核查日，InternNav README 列有 2026 年 1 月 v0.3.0 公告，以及此前公开的训练和部署入口。其表格明确区分 RGB / RGB-D、ShortestPathFollower、NavDP 与 DualVLN 等配置。这里保留配置区别，不把它们压缩成一个“InternNav 成功率”。[13]

NavFoM 探索跨任务、跨形态轨迹预测；其项目页明确写出真实系统使用 RTX 5090 远程服务器、网络传输和机器人本地规划器。[15] 因此“展示了机动机器人运行”不能改写为“模型全部运行于机载小算力设备”。

| 路线 | 中间接口 | 工程参考价值 | 主要边界 |
| --- | --- | --- | --- |
| NaVILA | 语言式高层命令 → 足式技能 | 高层语义与低层稳定性分工 | 学到的运动技能依赖机器人身体 |
| InternVLA-N1 / DualVLN | 像素目标 / 潜在计划 → 短程轨迹 | 异步更新、不同频率的决策 | 相机、特征、版本与控制器匹配 |
| NavFoM | 视频与任务 → 轨迹 → 本地规划器 | 多任务与形态条件化 | 远程算力和通信必须纳入时延 |
| 本文建议的工程基线 | 结构化子目标 → Nav2 Action | 便于日志、回退和替换模型 | 不等价于完整复现上述方法 |

设计双系统时，必须为计划附上时间戳、坐标系、有效期和撤销条件。旧计划不能在新目标已经产生后继续排队执行。下层被障碍阻断时，应反馈“不可达”或“需重定位”，而不是无限重试；上层也不能把低层发出的停止误读为任务已经成功。

## 08 · 数据与训练：扩大样本之前先固定任务语义 {#training}

ScaleVLN 利用更多三维环境生成指令—轨迹数据；其官方项目说明约 1200 多个场景、490 万组合样本。[17] 数据规模是一个变量，不代表经过更多语言包装就获得了独立的真实环境经验。

监督学习通常学习专家动作或局部轨迹；在线纠错数据则让模型见到自己偏离专家路径后出现的状态。StreamVLN 的公开配方包含导航专家数据、DAgger 以及一般多模态数据。[11] 模仿学习、纠错、预训练与强化学习的收益，必须在固定感知和执行接口后再做归因。

建议每条轨迹至少保存：原始指令和语言、相机内外参、观测时间、机器人位姿及来源、动作坐标系与单位、碰撞及停止事件、子目标、专家辅助和终止原因。不同平台的“前进”若对应不同距离与速度，直接拼成一个动作类别会引入隐性冲突。

**训练／测试应按场景划分，而不是只打散帧或轨迹。** 同一房间换一种指令表述，不等于未见环境。合成指令应检查地标可见、次序一致、参照系和路径可行；中文评测要专门处理“左前方”“第二扇门”“绕过去”“原路返回”等表达，不应由英语成绩直接外推。

推理、轻量微调和从头预训练是三种成本等级。本文不承诺某张消费 GPU 可复现所有论文：参数、精度、图像数、上下文和缓存共同决定显存。第一阶段只选择一份公开权重跑通固定输入，再测峰值显存、P50/P95 时延和长任务内存增长。

## 09 · Sim-to-Real：逼真的画面只是其中一项 {#sim-to-real}

VLN-PE 将观察视场、光照和机器人碰撞、跌倒等因素纳入评估，说明实际执行约束会改变导航结果。[16] Habitat 类环境适合大规模导航对照；引入物理机器人后，还要验证身体几何、控制周期和接触。不能把仿真中允许“滑过墙边”的代理，直接等价为有体积和制动距离的机器人。

| 差异 | 常见表现 | 建议的单变量验证 |
| --- | --- | --- |
| 视觉 | 镜面、低照、相机高度、视场差异 | 固定路线改变图像条件与安装参数 |
| 几何 | 门宽、楼梯、障碍高度、足迹 | 同目标更换机器人包络与安全裕量 |
| 动力学 | 转弯打滑、制动、足式跌倒 | 给定相同高层路径，比较控制跟踪 |
| 时间 | 推理慢、图像积压、网络抖动 | 延迟注入与丢帧，不暂停仿真掩盖等待 |
| 任务 | 指令有歧义、地标变化、目标搬走 | 固定环境，逐项改变任务条件 |

建议将真值地图或位姿分成两种用途：训练监督和诊断上限；正式测试观测则只开放任务允许的信息。使用真值低层跟随器可以隔离高层错误，但它只是一个诊断对照，不应作为可部署结果。

## 10 · ROS 2 / Nav2 接入：把语义提案变为受约束的目标 {#deployment}

以下是本文提出的工程架构，不是 InternNav 或 NaVILA 的官方集成包：

```text
语言指令 + 当前图像 + 任务记忆
  → 指令进度与空间候选
  → 目标解析、置信度、时间与几何校验
  → NavigateToPose / FollowWaypoints
  → 局部规划、控制与独立碰撞监测
  → 观察到达结果，推进下一步或触发恢复
```

Nav2 的 Simple Commander 提供目标发送、反馈、取消和结果查询。它解决导航执行接口，不负责理解“第二个门”或判断是否完成语言约束。[20] `map` 与 `odom` 的语义不同：全局重定位可能跳变，局部控制需要连续参考；应按观测时间查 TF，而不是用最新姿态解释很久以前的图像。[21]

建议将中间目标设计为明确的数据契约，而不是自由文本：

```yaml
# 设计示例，并非已经存在的 ROS 消息定义
subgoal_id: corridor-door-02
reference_frame: map
observation_stamp: REQUIRED
expires_after_s: CONFIGURED
relation: pass_through
object_instance: VERIFIED_OR_UNKNOWN
candidate_pose: VALIDATED_BEFORE_DISPATCH
abort_on: [stale_observation, map_jump, blocked_path, low_confidence]
success_requires: [navigation_result, visual_condition, instruction_order]
```

若没有可靠深度或地图定位，模型输出的像素点不能直接作为米制坐标。可采用限定步长的视向移动、重新观测与三角化，或先补齐几何链路。未知区域、没有观测的楼梯口和玻璃门不能被语义判断默认为可行。

Nav2 Collision Monitor 可以绕过规划器对传感器风险做减速或停止，但官方明确它不提供硬实时安全认证。[22] 因而还需要机器人本地失联保护、急停、驱动限速和人工接管；不能把 VLM 或单个软件节点称为完整安全系统。

## 11 · 失败恢复与记忆：停止不一定是失败，抵达不一定是成功 {#recovery}

建议将失败分为五类并保存证据：看错目标、路线理解错误、地图或坐标错误、执行不可达、结果判定错误。一个统一的“导航失败”计数，无法指导后续迭代。

| 状态 | 优先动作 | 不应采取的动作 |
| --- | --- | --- |
| 目标身份不确定 | 换视角或请求一次澄清 | 让低层盲走到高相似度目标 |
| 计划过期 | 撤销旧目标，重新关联状态 | 继续执行排队动作 |
| 目标不可达 | 检查地图与局部替代位姿 | 同一目标无限重发 |
| 指令顺序丢失 | 回查已验证事件和节点 | 仅凭模型叙述宣告已完成 |
| 长时无进展 | 停止并记录阻塞原因 | 延长动作块掩盖卡住 |

本文建议把“走过某门”“看见某标志”“到达可观察区域”等记录为带位置、时间和来源的事件。记忆中的缺失不等于事实不存在；旧观测也不保证目标还在。任务结束应同时检查导航执行、视觉/语义条件和需要遵循的路线顺序。

安全等待和主动回看可能增加路径长度，却避免错误操作。评测时应区分合理等待、规划振荡与重复探索，而不是把所有额外时间都归为模型低效。

## 12 · 指标与对照：成功率只是第一列 {#evaluation}

SPL 将任务成功与相对最短路径长度结合；nDTW 则用轨迹对齐刻画路径遵循。后者比较的是实际路径与参考路径，并不直接判断语言是否被正确理解。[18][19]

```text
SPL = (1/N) · Σ_i S_i · L*_i / max(L_i, L*_i)
nDTW = exp( -DTW(reference_path, executed_path) / (len(reference_path) · d_threshold) )
```

这里 `L*_i` 是协议中的参考最短可行距离，`S_i` 是该任务定义的成功指示量；初始即在目标的退化情况应使用评测实现的约定。不要把存在绕路要求的语言路线机械当作最短路问题。

| 指标 | 回答的问题 | 必须附带的条件 |
| --- | --- | --- |
| SR / NE | 是否到达；离目标多远 | 距离口径、停止阈值、超时 |
| Oracle success | 路途中是否曾进入目标邻域 | 不能替代最终自主停止成功 |
| SPL | 成功任务是否高效 | 最短路与实际轨迹如何计算 |
| nDTW / sDTW | 是否遵循参考路线 | 参考路径、采样方式、容差 |
| 碰撞／干预 | 运行代价和风险如何 | 次数、距离或时间分母、干预类型 |
| P50 / P95 完成时间 | 用户实际等待多久 | 包含推理、通信、重试与恢复 |
| 资源占用 | 是否能稳定部署 | 硬件、精度、显存、缓存长度 |

最低限度的对照是：相同场景和起终点、同一观测、同一控制器、同一任务预算，单独改变规划或记忆模块。还应做“语言打乱／删去历史／真值子目标／真值定位”等诊断消融，区分数据偏差、语言贡献、几何误差与执行瓶颈。

## 13 · 可执行原型：先验证语义落地，再提高模型复杂度 {#prototype}

下表是研究建议，不是已经完成的实验或交付承诺。先用自有或获授权的小型场景，不因公开仓库可访问就假设全部场景数据无使用条件；VLN-CE 的 README 明确给出了独立的场景和数据准备步骤。[24]

| 阶段 | 最小产出 | 进入下一阶段的条件 |
| --- | --- | --- |
| A · 导航基线 | 固定地图和目标，几何导航与日志回放 | TF、时间、碰撞、取消指令可检查 |
| B · 语义目标 | 少量已确认地标 → 可达观察点 | 不把对象中心误当通行目标 |
| C · 组合指令 | 门、走廊、地标的有序子任务 | 每个子任务有进入与成功判据 |
| D · 记忆与恢复 | 重复走廊、目标移动、局部封路 | 能识别失败类型并有限次恢复 |
| E · 模型对照 | 在同一接口替换本地视觉语言策略 | 完整任务收益而非单步预测收益 |
| F · 物理与实机 | 延迟、传感器、身体与动力学扰动 | 仿真日志、限速、急停、接管机制齐全 |

可从 20—30 条固定中文指令、若干相似门口和重复路线开始。这是实验规模建议，不是统计上充分的可靠性证明。先设计预注册的成功判据与测试划分，报告每类样本数，再逐步扩大任务。

建议的三个研究切口：**空间目标落地与不确定性、任务进度与地图记忆的一致性、异步计划的过期和失败恢复。** 它们能利用三维视觉和机器人系统经验，也较容易构造可解释的消融。

本报告编写与网页阅读不需要模型 API。未来复现某项研究时，应另行核对它是否依赖在线商业模型、远程算力或受许可数据；采用本地替代模型可能改变实验条件，不能继续沿用论文成绩。不要以“没有 API 费用”掩盖本地 GPU、存储和维护成本。
